# Docker 部署与 SQLite 备份设计规格

## 目标

为 Baby Feed 增加一条可重复执行的远程部署命令。部署从本机完成生产校验、`linux/amd64` 镜像构建、压缩上传、远程备份、容器切换和健康检查，并在新版本启动失败时自动恢复上一应用版本。

SQLite 数据必须独立于镜像和容器持久化。每次替换应用前允许约 5-15 秒正常停机，以获得包含主数据库、WAL 和 SHM 文件的一致备份。应用回滚不得自动覆盖数据库。

## 已确认环境与决策

- 本机是 `arm64`，Docker Buildx 可构建并加载 `linux/amd64` 镜像。
- 远程宿主机是 `x86_64`，Docker 26.1.3 和 Docker Compose v2.27.0 已安装、启用并正常运行。
- 当前应用由 systemd 管理，服务目录是 `/opt/baby-feed`，端口是 `9001`。
- 当前 SQLite 数据位于 `/opt/baby-feed/data`，数据库采用 WAL 模式，线上已有主文件、`-wal` 和 `-shm` 文件。
- 采用“本机构建镜像并上传”的发布方式，不使用远程源码构建或外部镜像仓库。
- 用户接受正常发布约 5-15 秒停机；异常发布可能在最长约 60 秒健康检查后回滚。

规格和脚本不得包含远程主机密码、私钥或其他登录凭据。远程地址从本地、忽略提交的配置文件读取。

## 交付组成

实现包含以下聚焦文件：

- `Dockerfile`：多阶段生产镜像，构建和运行环境均使用 Linux glibc Node 镜像，确保 `better-sqlite3` 原生依赖与目标平台一致。
- `.dockerignore`：排除 Git 元数据、本地构建产物、测试缓存、部署配置和所有 SQLite 数据文件。
- `deploy/compose.yaml`：定义应用容器、端口、环境变量、数据绑定、重启策略和健康检查。
- `deploy/remote-release.sh`：只在远端执行发布状态切换、备份、健康检查、保留清理和自动回滚。
- `scripts/deploy.sh`：本地统一入口，提供 `check`、`deploy` 和 `rollback` 子命令。
- `.env.deploy.example`：记录非敏感配置项示例；真实 `.env.deploy` 加入 `.gitignore`。
- `src/app/api/health/route.ts`：提供不泄露业务数据的应用和 SQLite 健康检查。
- 自动化测试：覆盖脚本参数、执行顺序、失败恢复、健康接口和持久化行为。

`package.json` 增加 `deploy` 命令，日常发布入口为：

```bash
pnpm deploy
```

等价于执行 `bash scripts/deploy.sh deploy`。诊断和手动应用回滚分别使用：

```bash
bash scripts/deploy.sh check
bash scripts/deploy.sh rollback
```

## 配置接口

本地 `.env.deploy` 支持以下配置：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `DEPLOY_TARGET` | 无，必填 | SSH 目标，格式由本机 SSH 支持，例如 `user@host` 或 SSH config 别名 |
| `DEPLOY_DIR` | `/opt/baby-feed` | 远程应用根目录 |
| `APP_PORT` | `9001` | 宿主机和应用监听端口 |
| `BACKUP_KEEP` | `10` | 保留的数据备份份数 |
| `IMAGE_KEEP` | `3` | 保留的 Baby Feed 应用镜像数，包含当前版本 |
| `HEALTH_TIMEOUT` | `60` | 新版本健康检查超时秒数 |

脚本使用系统 `ssh` 和 `scp`，启用严格主机密钥检查。认证由用户现有 SSH agent、密钥或交互式密码提示完成；脚本不读取、保存或回显密码。

## 镜像与 Compose 结构

本地镜像以 Git commit SHA 标记，例如 `baby-feed:<sha>`。发布脚本检测到已跟踪文件修改时必须显式失败，避免镜像标签与源码内容不一致；不相关的未跟踪文件由 `.dockerignore` 排除。

构建使用：

```bash
docker buildx build --platform linux/amd64 --load
```

构建阶段运行冻结锁文件安装和生产构建。运行阶段只包含启动所需的 `.next`、`dist`、`public`、生产依赖及元数据，并以固定 UID/GID `10001:10001` 的非 root 用户运行。镜像必须包含在目标平台安装的 `better-sqlite3`，不能复制本机 `node_modules`。

Compose 的核心约束为：

- 镜像标签通过远端发布环境文件注入，不使用 `latest` 作为发布身份。
- 宿主机端口保持 `9001`，容器内使用相同应用端口。
- `HOSTNAME=0.0.0.0`，`DEPLOY_RUN_PORT` 使用配置的应用端口，保持与现有自定义服务入口一致。
- `SQLITE_PATH=/app/data/baby-feed.sqlite`。
- `/opt/baby-feed/data:/app/data` 作为宿主机绑定挂载，直接沿用现有数据目录，不进行路径迁移。
- 容器以 `10001:10001` 运行；首次切换前在备份成功后调整数据目录所有权，原 systemd root 服务仍可在失败时读取和写入该目录。
- 容器使用 `restart: unless-stopped`。
- Compose 健康检查请求容器内 `/api/health`。

远端稳定文件放在 `/opt/baby-feed/deploy`，传输中的镜像放在 `/opt/baby-feed/incoming`，备份放在 `/opt/baby-feed/backups`。稳定发布状态记录当前和上一成功镜像标签，只有健康检查成功才轮换这两个标签。脚本只清理这些明确目录内由自身命名的旧文件，不执行全局 Docker prune 或宽泛递归删除。

## 健康检查

`GET /api/health` 执行轻量 SQLite 查询以确认以下条件：

- Next.js 服务已开始处理请求。
- `better-sqlite3` 可以加载。
- 持久化目录可访问，目标数据库可打开并执行 `SELECT 1`。

成功返回 HTTP 200 和固定状态字段；失败返回 HTTP 503。响应不得包含数据库路径、房间、记录或异常堆栈等敏感信息。

远端发布脚本同时检查 Compose 容器健康状态和宿主机 `APP_PORT` 的健康接口，防止只在容器内部可用但端口映射失败。

## 正常发布流程

1. 本地读取并校验 `.env.deploy`，取得部署锁前不改变远端状态。
2. `check` 阶段验证 Git 状态、本机 Docker/Buildx、远端 SSH、Docker Compose、磁盘空间和部署目录权限。
3. 本地运行现有测试、类型检查和构建校验。
4. 使用 Buildx 构建 `linux/amd64` 镜像，以当前 Git SHA 标记。
5. 使用临时目录执行 `docker save` 和压缩；上传镜像包、Compose 文件和远端脚本。
6. 远端取得专用文件锁，先完成镜像校验和 `docker load`。任何上传、加载或预检失败都在停机前结束，线上服务保持不变。
7. 记录当前成功镜像标签；首次 Docker 化时记录当前 systemd 服务状态。
8. 进入停机窗口：首次部署停止 systemd，后续部署停止当前 Compose 应用，并等待进程退出。
9. 将整个 `/opt/baby-feed/data` 归档到新的备份目录，同时保存旧镜像标签、Compose 文件和发布元数据。归档失败时立即恢复旧应用并终止发布。
10. 备份成功后校验数据目录的真实路径位于 `DEPLOY_DIR` 下，并将其所有权调整为容器固定 UID/GID `10001:10001`。
11. 原子更新远端发布环境文件为新镜像标签，执行 Compose 启动。
12. 在 `HEALTH_TIMEOUT` 内轮询健康状态。成功后才将旧当前标签记录为上一成功版本，并将新标签记录为当前成功版本。
13. 首次 Docker 化成功后禁用旧 systemd 服务，避免服务器重启时与 Compose 争用端口；不删除 service 文件和旧源码。
14. 仅清理超出保留数量的 Baby Feed 备份、上传包和应用镜像。

构建、压缩、上传和镜像加载均发生在停机前。正常停机窗口只包含停止旧进程、归档小型 SQLite 数据目录、创建容器和健康检查。

## SQLite 备份与持久化

备份目录命名包含 UTC 时间和旧应用标签，例如：

```text
/opt/baby-feed/backups/20260826T020304Z-1a758fb/
```

每份备份至少包含：

- `data.tar.gz`：停止唯一写入进程后打包的完整数据目录，包括主数据库、WAL、SHM 及未来同目录数据文件。
- `release.env`：旧应用镜像标签和发布元数据，不含凭据。
- `compose.yaml`：发布前使用的 Compose 定义。

数据目录从不复制进镜像、镜像压缩包或本地机器。替换、删除容器不会删除宿主机绑定目录。

默认保留最近 10 份完整数据备份。保留清理按成功创建且命名合法的备份目录排序，只删除超出数量的最旧目录；清理失败仅告警，不使已经健康的发布回滚。

## 回滚行为

### 自动回滚

新容器在超时内未健康时：

- 后续 Docker 部署将发布环境文件切回上一成功镜像，并重新执行 Compose 启动。
- 首次 Docker 化将停止失败容器并重新启动原 systemd 服务。
- 输出新容器最近日志和明确失败阶段。
- 不恢复 `data.tar.gz`，不覆盖当前 SQLite 数据。

自动回滚成功后命令仍以非零状态退出，使调用者知道新版本没有发布成功。

### 手动应用回滚

`scripts/deploy.sh rollback` 在切换应用前再创建一份当前数据库备份，然后切换到上一成功镜像并执行相同健康检查。该命令只回滚应用。

数据库恢复属于独立、破坏性操作，不由普通部署或应用回滚命令自动执行。本次仅在运维说明中给出显式恢复步骤，要求先停止写入进程、再次备份当前数据并明确选择备份编号。

## 错误处理

| 失败阶段 | 线上影响 | 处理 |
| --- | --- | --- |
| 本地校验、构建或压缩失败 | 无 | 清理本地临时文件并退出 |
| SSH、上传、远端预检或镜像加载失败 | 无 | 保持旧服务运行并退出 |
| 取得部署锁失败 | 无 | 提示已有部署进行中并退出 |
| 停止旧服务失败 | 可能仍在线 | 不备份、不启动新版本，报告状态 |
| 数据备份失败 | 短暂停机 | 恢复旧容器或 systemd 后退出 |
| 新版本健康检查失败 | 最长约 60 秒停机 | 自动恢复上一应用版本，保留数据和失败日志 |
| 自动应用回滚也失败 | 服务不可用 | 保留旧镜像、备份和日志，输出可直接执行的恢复命令，不修改数据库 |
| 备份或镜像保留清理失败 | 无 | 发布保持成功，仅输出告警 |

所有 shell 脚本使用严格错误模式、明确路径和可验证参数。临时文件通过 `mktemp` 创建并由退出 trap 清理。破坏性操作不得以空变量、未解析通配符、用户主目录或文件系统根目录为目标。

## 测试设计

自动化测试遵循先失败、再实现的顺序，至少覆盖：

- 配置校验：缺少 `DEPLOY_TARGET`、非法保留数量、非法端口时在任何远端写操作前失败。
- 本地命令：构建命令明确包含 `--platform linux/amd64` 和 Git SHA 标签。
- 执行顺序：镜像加载发生在停服前；停服发生在备份前；备份成功后才允许启动新版本。
- 首次迁移：新版本成功后禁用 systemd；失败时重新启动 systemd。
- 后续部署：健康检查失败时恢复上一成功镜像，且不执行数据库恢复。
- 备份失败：旧应用恢复，发布退出非零。
- 保留策略：只删除超额且命名合法的 Baby Feed 备份和镜像，不调用全局 prune。
- 健康接口：SQLite 正常时返回 200，数据库不可打开时返回 503，响应不泄露内部错误。
- 持久化烟雾测试：使用临时宿主机目录启动容器，写入一条测试记录，替换容器后确认记录仍存在。

验证命令包括：

- shell 语法检查；环境存在 ShellCheck 时执行静态检查。
- `pnpm test`、`pnpm run validate` 和 `pnpm run build`。
- 实际构建 `linux/amd64` 镜像并检查镜像架构。
- 使用临时数据目录执行本地 Compose 健康和持久化测试。
- 对真实远端执行只读 `scripts/deploy.sh check`；测试本身不自动触发生产部署。

## 验收标准

- 首次配置 `.env.deploy` 后，`pnpm deploy` 可以完成构建、上传、备份、切换和验活。
- 镜像架构是 `linux/amd64`，远程容器可加载 `better-sqlite3` 并健康运行。
- 现有 SQLite 数据继续从 `/opt/baby-feed/data` 读取；替换容器后房间和记录仍存在。
- 每次进入应用切换前产生可识别、可解包的完整数据备份。
- 正常部署停机约 5-15 秒；耗时的构建、上传和加载不占用停机窗口。
- 新版本失败时上一应用版本自动恢复，数据库不被自动覆盖。
- `check`、`deploy` 和 `rollback` 均输出当前阶段、版本和最终结果，不输出密码或业务数据。
- 重复执行部署是幂等的，不会重复迁移或删除现有数据库。
- 所有自动化测试、项目校验、生产构建、镜像构建和本地容器持久化验证通过。

## 非目标

- 不引入 GitHub Actions、阿里云容器镜像服务或其他镜像仓库。
- 不配置域名、TLS、反向代理或防火墙。
- 不自动修改 SSH 登录方式、服务器安全更新或 OpenClaw 服务。
- 不自动恢复数据库备份。
- 不改造现有 SQLite schema 或业务数据模型。
- 不在测试流程中自动发布到生产服务器；生产发布只由用户显式执行 `pnpm deploy` 触发。
